## Findings: the evidence

The only committed reproduction records are six runs of `q1-sparse-medium` (SMRT Fig. 3) on
`qwen-plus`, three with the full harness and three with the raw baseline (the same LLM with no
harness). The judge was `anthropic/claude-opus-5`, label-blinded.

| Measure | Full harness | Raw baseline |
|---|---|---|
| Figure produced | 3/3 | 0/3 |
| Visual judge (0–8) | 8, 8, 8 | not scoreable |
| Report judge (0–10, pass ≥ 8 with factuality 2) | 6, 6, 5 (all fail) | 4, 2, 0 (all fail) |
| LLM calls / tokens / wall time | 26–28 / 0.65–0.74 M / 4–5 min | 3 / ~8 k / 11–13 s |

What this shows:

1. **The harness fixes the computation but not the narration.** Every harnessed report scored
   factuality 1/2. The reports claimed "numerically verified" when the numeric score was not
   scoreable, described linear axes as log–log, and said the chart "matches exactly" when the
   legend and caption checks had failed.
2. **The visual judge is lenient.** It gave 8/8 to a figure whose sticky-hard-sphere curves end
   about 25% below the paper's (≈0.019 against ≈0.025 m⁻¹). A qualitative judge needs a numeric
   gold standard beside it.
3. **The cost is about 85× the baseline's tokens**, because the prompt grows from 14 k to 39 k
   tokens over 28 calls.

## What a reviewer will ask

- **Scale.** The evidence is n = 3, one LLM and one task. Needed: 6–8 cases × ≥ 4 LLMs × 4
  configurations × 5 repeats, with bootstrap confidence intervals and paired tests (the design
  is already blocked by task).
- **Numeric gold.** Rerun the authors' code or digitise the published curves, and score
  normalised RMSE.
- **Judge validity.** Have two domain experts rate about 30 runs and report Cohen's κ against
  the LLM judge.
- **Baseline strength.** "The same LLM with no tools" is a weak baseline. The fair one is a
  general coding agent (Claude Code, Codex) given the same SMRT package and the same PDF.
- **Leakage.** The SMRT paper (2018) is almost certainly in pretraining data. Add
  counterfactual variants (change the radius or frequency and regenerate the gold with the
  oracle) and one paper published after the models' training cutoff.

## Plugins for Claude Code, Codex and DeepSeek

"Plugging in DeepSeek" can mean two things:

- **DeepSeek as the backbone of our own agent** works today. `agent/completion.py` uses an
  OpenAI-compatible client configured by `PHYSEARTH_LLM_API_BASE`, `PHYSEARTH_LLM_MODEL` and
  `PHYSEARTH_LLM_API_KEY`.
- **Someone else's agent as the host** needs one MCP server (`physearth-mcp`, stdio) over
  `physearth.api`. That covers:
  - Claude Code, as a plugin: `.claude-plugin/plugin.json`, `.mcp.json`, skills generated
    from `knowledge/skills/`, a `/reproduce-figure` command, and a Stop hook.
  - Codex CLI, through `[mcp_servers.physearth]` in `~/.codex/config.toml`.
  - Any MCP-capable client running on DeepSeek, Qwen or GLM.

Most invariants carry over unchanged because they already live in code: parameter ranges and
QC bounds, handles instead of arrays, and charts drawn from a declarative spec. Two need a
redesign, because the host is outside our loop:

- **Human approval.** The host model can call any tool we expose, so a run tool should return
  a pending ticket that is approved out of band, through MCP elicitation or a local CLI or
  page. No approve tool is exposed.
- **The citation gate.** The host writes the final answer, so expose `verify_report(text)` and,
  in Claude Code, a Stop hook that blocks until it passes.

The host's own web search sits outside our boundary for untrusted text, and the paper should
say so.

A side benefit: "Claude Code or Codex with and without PhysEarth, on the same task" is the fair
baseline the evaluation currently lacks.

## Further suggestions

1. **A numeric claim gate.** Every number in a report cites a result handle and must match it
   within a tolerance. This extends the existing marker mechanism from sources to values.
2. **Uncertainty by default.** Sweep the parameters a paper leaves unstated (stickiness, depth,
   36.5 or 37 GHz) and report a band.
3. **An onboarding benchmark.** Someone new registers a seventh model; measure the hours and
   lines it takes, with zero harness edits.
4. **An expert user study.** Six to eight snow and soil scientists: errors caught and time to a
   correct figure, compared with a notebook.
5. **Release it as a benchmark.** Tasks, oracles, judge standards and run records with a DOI,
   plus a small leaderboard.
6. **Cost controls.** Prompt caching and context compaction; report an accuracy-against-tokens
   frontier.

## Proposed order

1. Weeks 1–2, repair: restore the runners, get the suite green, add CI, make build IDs clean,
   fix the docs.
2. Weeks 3–6, cases: add the cases above with numeric gold, and extract figures for all papers.
3. Weeks 7–9, hosts: the MCP server and plugins, approval tickets, `verify_report`.
4. Weeks 10–12, experiments: the full matrix, judge calibration, the user study, and the
   writing.

The venue decides the framing. An ML benchmark track or an AI-for-science workshop wants the
benchmark, the baselines and the judge calibration. A geoscience model journal such as GMD,
where SMRT itself was published, wants physical fidelity and the registration contract.
