PhysEarth-Agent — four ways to lay out the repository

A read of the repository as it stands, the constraints the code actually imposes on any reorganisation, four candidate structures, and one recommendation — a backend/frontend split with layered prompts, a user-facing models/ registration folder and a slimmed evaluation/.

358 tracked files · 15,388 lines of Python · 18 top-level entries Branch main

Section 01Where the repository is today

The physics, the harness and the evidence are in good shape. What has drifted is the shape: one flat package holds nine concerns, the interface is spread over three places, and the two folders a visiting scientist is most likely to open — evaluation and model registration — are the two with the most clutter in front of them.

assets/             ui.css, ui.js, fonts — frontend, but detached from app.py

  • Frontend and backend are interleaved, not separated.Only app.py imports Gradio — that is a real asset — but the HTML lives in physearth/ui/, the CSS/JS in assets/, and the session and archive logic that belongs to the backend lives inside app.py's event handlers.
  • The prompt has levels already; the file system does not show them.prompt.py concatenates identity (ROLE, STYLE), policy (CITATION_RULES, ONLINE_RULES, ABSTRACT_RULE), workflow (WORKFLOW, RESEARCH_WORKFLOW, TRIGGERS) and runtime context (status_block, models_section). Two more levels live elsewhere: method notes in knowledge/skills/ and task profiles in evaluation/prompts/. Editing a rule means editing Python.
  • Model registration is the headline feature and the hardest thing to find.The pitch is "register a model and it inherits the whole system", but a newcomer must open physearth/models/bundled/smrt/ for a real card, examples/toy_model/ for the minimal one, and physearth/models/contract.py for the rules.
  • evaluation/ carries two taxonomies for the same thing.tasks/{tier0,tier1,tier2,probe,reproduction}/ and tiers/{t0_registry_integrity,…,t3_independent_reproduction}/ are separate trees with different names for overlapping ideas, plus 12 runners and seven loose files at the folder root. This is the folder you want a user to read and modify.
  • Four modules are doing too much.research.py alone holds plan proposal, parameter repair, evidence checking, chart validation, review actions and protocol export — 3,552 lines, ~90 functions, no seams.
  • Import paths are held together by sys.path inserts.Ten of them across evaluation/runners/, evaluation/metrics/ and tests/. Any restructuring should retire them rather than move them.

Section 02What is not negotiable

Four facts in the code constrain every option below. I checked each one rather than assuming it.

ConstraintWhereWhat it means for a move
deployspec: entry_file: app.pyREADME front-matter (ModelScope Studio) A file named app.py must remain at the repository root. It can be a three-line shim.
packages = ["physearth"]pyproject.toml, hatchling Moving the package requires the wheel target and any data folders to move with it.
Path(__file__).parent.parent / "knowledge"knowledge.py, reference.py, model_guidelines.py Three hard-coded relative jumps out of the package. They break silently — no import error, just an empty corpus — so they need a single resolved root, not three edits.
Registry discovery by directorymodels/registry.py: BUNDLED_DIR, PHYSEARTH_MODEL_PATH, entry-point group Wherever model cards land, that path constant and the packaging data-include must agree, or a deployed wheel loses its bundled models.

Section 03What production teams converge on

The current consensus for a shipped agent is narrower than the framework marketing suggests. Four patterns recur:

Prompts as versioned files, not string constants

Prompt text lives in Markdown/YAML under a prompts/ directory with a registry file, so it can be diffed, reviewed and pinned to a run record. A hash of the assembled prompt is logged with every call.

Evals as a first-class sibling of source

A top-level evaluation tree with tasks, metrics and committed results, runnable in CI with one command. Not notebooks, not a private dataset.

One importable core, thin deployables

src/-style package for the agent; UI, API and CLI are thin entry points over it. The core never imports the web framework.

A written map at the root

AGENTS.md — canonical commands, entry points and boundaries — now read by most coding agents, and just as useful for humans.

Sources at the foot of this page. The structure below is this repository's version of those four, not a copy of any one template.

Section 04Four options

Option A — Consolidate in place

1 daylowest riskpartial fit

Keep every top-level folder where it is. Split only the four oversized modules into subpackages inside physearth/, and delete the clutter.

physearth/
  agent/      loop.py stream.py messages.py faults.py __main__.py
  research/   plan.py repair.py review.py coverage.py protocol.py
  tools/      literature.py models.py charts.py data.py
  prompts/    identity.md policy.md workflow.md context.py
  ui/ ingest/ models/ schemas/     unchanged
app.py assets/ evaluation/ knowledge/ tests/     unchanged

Buys you

  • No import paths change outside the split modules
  • Tests, runners and the deployspec keep working untouched
  • The 3,552-line file problem is genuinely solved

Costs you

  • Frontend and backend stay mixed — your first requirement is unmet
  • Model registration stays buried three levels deep
  • evaluation/ stays as cluttered as it is

Option B — Audience-first flat top level

3–4 daysmedium riskmost readable

Organise the root by who opens the folder, with no package nesting at all. Every audience gets one directory, one level down from the root.

agent/          the loop, tools, harness — the standalone backend
prompts/        every prompt layer, as files
models/         registration: contract, template, bundled cards, examples
evaluation/     tasks, metrics, runners, results
frontend/       Gradio app, views, css/js/fonts
knowledge/      literature and method notes
docs/  tests/  app.py

Buys you

  • The root reads like a table of contents — nothing to explain
  • Every one of your five requirements is visible at depth 1
  • Shortest possible path to any file a user wants to edit

Costs you

  • Breaks the installable package: pip install physearth-agent no longer gives one importable namespace, and agent/models are far too generic as top-level Python module names — a genuine collision risk on sys.path
  • All 358 tracked files' imports churn at once
  • Publishing a wheel later means redoing this

Option C — Backend / frontend split, layered inside

Recommended4–6 days, phasedmedium risk

Two roots — backend/ and frontend/ — with the installable package living under backend/physearth/. The three folders a user reads and edits (prompts/, models/, evaluation/) are lifted to the top level as content, while the code that interprets them stays in the package. Full tree in Section 06.

app.py            3-line shim — satisfies the ModelScope deployspec
frontend/         Gradio wiring, views, static assets
backend/physearth/ the importable package; never imports gradio
prompts/          L0…L4, one file per level
models/           README, contract, TEMPLATE, bundled/, examples/
evaluation/       one entry point, one taxonomy
knowledge/  docs/  tests/

Buys you

  • All five of your requirements, each at depth 1
  • python -m physearth.agent "question" runs headless — enforceable by a test that no backend file imports Gradio
  • Prompts and model cards become editable content, not source code
  • The wheel still ships one clean physearth namespace

Costs you

  • Content outside the package must be force-included in the wheel — one pyproject block, and it must be tested by building the wheel, not by assuming
  • Roughly 60 files move; history stays via git mv
  • Needs the phased migration in Section 10 to stay green throughout

Option D — Full monorepo (apps/ + packages/)

2 weeks+high riskpremature

The layout most large teams end at: several independently versioned packages and several deployables, wired by a workspace.

apps/studio/    apps/api/    apps/cli/
packages/physearth-core/     packages/physearth-models/
packages/physearth-eval/     packages/physearth-knowledge/

Buys you

  • Model registry could ship as its own package for third parties
  • A future HTTP API deploys separately from the Studio

Costs you

  • There is one deployable today, and one maintainer — the cross-package version dance is pure overhead
  • Every evaluation runner grows a workspace dependency
  • Worth doing the day a second deployable actually exists; Option C is a clean subset, so nothing done now is wasted

Section 06Recommendation — Option C, in full

Take Option C. It is Option B's readability without Option B's packaging problem: the folders a user opens are at depth 1 as content, and the code that reads them stays inside one importable package. Option A is the fallback if you want the file-size problem solved this week and nothing else touched.

Section 07Prompts, by level

Five levels, ordered from the least to the most task-specific. Each is a file a scientist can edit without opening Python; backend/physearth/prompts.py only concatenates them and records the hash of what it built into the run record.

The payoff beyond tidiness: the ablation configs (no-harness, no-capability, no-literature) stop being a switch statement in Python and become a declaration of which levels were loaded — which is also exactly what a run record should carry to make the evaluation reproducible.

Section 09models/ — registration, for reading

This is the repository's headline claim, so it should be the shortest path from the root. The mechanism moves into backend/physearth/registry/; the content — the thing a scientist copies — comes to the top.

models/
├─ README.md              register a model in five minutes; the tier table; PHYSEARTH_MODEL_PATH
├─ CONTRACT.md            the card schema in prose, next to the JSON schema it describes
├─ TEMPLATE/              copy this folder → model_card.yaml + adapter.py, TODOs marked
├─ examples/toy_model/    ← examples/ — the minimal working registration
└─ bundled/               ← physearth/models/bundled/
    smrt/ tau_omega/ water_cloud/ pywatershed/ prosail/ pyet/
        model_card.yaml   adapter.py   README.md

The one thing to get right: models/ now sits outside the package, so the wheel must force-include it and registry.BUNDLED_DIR must resolve through a single paths.py helper that works both from a checkout and from an installed wheel. That is the main technical risk in this whole proposal, and it is verified by building the wheel and importing from a clean venv — not by reading the config. If you would rather not carry it, the alternative is to leave bundled/ inside the package and have top-level models/ hold only the README, contract, template and examples. Slightly less tidy, zero packaging risk.

Section 10Migration — six phases, green at each one

Every phase is one commit, moved with git mv so blame survives, and ends with the full test suite passing plus a launched Studio.

  1. Clean and document Remove dummy/, stray output_no_cascades/, .DS_Store, root __pycache__; move TODO.md, tasks/*.md and the two design HTMLs into docs/; write AGENTS.md. No code moves. Verify: pytest unchanged.
  2. Split the four large modules in place research.py, tools.py, agent.py, ui/render.py become packages, each __init__.py re-exporting the old names so nothing else changes yet. This is Option A, and it is independently valuable if you stop here. Verify: pytest, no import edits outside the split.
  3. Lift the frontend app.py → frontend/studio.py + root shim; physearth/ui/ → frontend/views/; assets/ → frontend/static/; add the "no gradio in backend" test. Verify: Studio launches, UI tests updated for the new asset paths.
  4. Move the package under backend/ Update the hatchling wheel target, introduce paths.py as the single resolver for knowledge/, models/ and prompts/, drop the sys.path inserts. Verify: build the wheel, import from a clean venv, run tier0.
  5. Extract prompts to levels L0–L2 to Markdown, L4 from knowledge/skills/, L5 from the eval prompt profiles; prompts.py assembles and hashes. Verify: the assembled prompt is byte-identical to today's for the default profile — assert it in a test before deleting the constants.
  6. Consolidate models/ and evaluation/ Merge the two eval taxonomies, add run.py, lift the model cards and template. Verify: tier0 and the registration runner reproduce their committed JSON exactly.

Phases 1–2 are safe to do immediately. Phase 5's byte-identical check is what keeps a prompt reorganisation from quietly becoming a behaviour change — worth insisting on.

Section 11What I need from you before starting

  • Option C, or A first? A is a subset of C (it is phase 2), so starting with A costs nothing if you later want C.
  • backend/physearth/ or the conventional src/physearth/? Identical mechanically; backend/ reads better next to frontend/, src/ is what a Python packaging tool expects. I lean backend/ for this repo, because the audience is scientists rather than packagers.
  • Bundled model cards outside the package, or inside? Outside is tidier and needs the wheel force-include; inside is zero-risk. Section 09.
  • Is anything pinned to the current paths outside this repo? The ModelScope deployment, a CI workflow, or a citation pointing at a file URL — those set the shims I need to leave behind.
