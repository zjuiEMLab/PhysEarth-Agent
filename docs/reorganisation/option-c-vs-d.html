Option C vs Option D

If the monorepo is the destination, is the backend/frontend split throwaway work? I measured the repository's internal import graph to answer it rather than estimate.

No — and the sequence C → D is cheaper in wall-clock than going straight to D. About 80% of Option C is work Option D requires verbatim, because the expensive part of a monorepo is decoupling, not directories. C does the decoupling while the code is still one importable namespace, where a mistake is an ImportError you fix in seconds instead of a version resolution failure across four distributions. Roughly 1–1.5 days of C's 6 would be redone. Separately: on today's evidence D is not a destination this repository has earned yet.

Section 01What the import graph actually says

I parsed every import inside physearth/ into a dependency graph. Four findings decide this comparison.

  • The graph is a DAG. No cycles, at any level. 25 modules, 24 internal edges, zero cycles. This is the precondition for any package split — and it is why D is possible at all. It also means C is not fighting the code; both options are building on the same clean skeleton.
  • models/ is already one edge away from being its own package. Everything under physearth/models/ imports only its own contract and registry — with exactly one exception: bundled/pywatershed/adapter.py:53 does a lazy from physearth import config inside a function. Ten modules import into models. So the dependency arrow already points the right way for a split, and a single edge stands between here and a standalone model distribution.
  • One core module reaches into a bundled model's private internals. diagnostics.py:140 imports _ensure_smrt_importable from models.bundled.smrt.adapter — an underscore-private function, from a specific model, in a warm-up path. Under C this is untidy. Under D it is a cross-distribution import of a private symbol: illegal, and it needs a public warm-up hook on the registry before the split can happen.
  • evaluation/ is a pure consumer — nothing imports it. It reaches into 8 core modules (agent, approval, config, harness, research, results, tools, validation) plus models.registry and models.contract, and has zero fan-in. It is the easiest thing in the repo to lift into its own package, under either option, and no other work depends on doing so.

Section 03What is genuinely thrown away

Being precise about this, because "nothing is wasted" would be a sales answer rather than a true one.

Redone ≈ 1–1.5 days

  • backend/physearth/ becomes packages/physearth-core/src/physearth/ — one git mv and a pyproject edit
  • Top-level models/ and prompts/ move inside their owning packages, and the wheel force-include written for them is deleted
  • The single pyproject.toml is replaced by five

Carries over intact ≈ 4.5–5 days

  • The four module splits — D cannot draw a package boundary through a 3,552-line file
  • The frontend facade — it becomes the core package's public __init__
  • paths.py and the removal of 10 sys.path inserts — D is strictly harder without this
  • Prompt levels, eval taxonomy, model template and README — content, boundary-agnostic

So the question "is C meaningless if D is the target" has a numeric answer: roughly 20% of C is layout that D would redo, and 80% is decoupling that D presupposes. There is no version of D that skips the 80%.

Section 04The prior question — has this repo earned D?

A four-package monorepo is not a tidiness upgrade; it is a coordination cost you take on in exchange for independent release. Six conditions normally justify it. Scored against the repository as it stands:

  • ✗More than one deployable There is one Gradio Studio, and the README front-matter pins entry_file: app.py. No API, no worker, no second surface.
  • ~Third parties install one piece without the rest Not happening today — but it is the stated ambition: "breadth is meant to come from the registration mechanism". If someone should be able to pip install physearth-models and register against the contract without pulling Gradio, that is the one argument for D with real force. It argues for two packages, not four.
  • ✗Separate release cadences or separate teams One maintainer, one cadence. Cross-package version pinning here is pure ceremony.
  • ~Irreconcilable dependency conflicts The strongest technical signal present. smrt is registered as tier: local with requires_import, and its adapter carries a Python-3.13 workaround that mutates sys.modules["numba"] during import. .gitignore still references .venv-pws, "the isolated environment for the numpy-2 model". Models are already straining against a shared process. But the fix for that is per-model environments or subprocess isolation — which is a runtime decision, not a repository layout.
  • ✗Build or CI time is painful 15k lines, a test suite that runs in seconds, and a Tier-0 suite that costs nothing. Nothing to parallelise.
  • ~Licence or redistribution boundaries knowledge/ is 98 files of CC-BY literature redistributed under per-paper attribution in NOTICE, sitting inside an Apache-2.0 codebase. Separating data from code has a real rationale — and again it argues for one extra distribution, not four.

Reading of the score: three "no", three "partial", zero "yes" — and every partial points at the same seam, which is models-and-data versus the agent. None of them points at splitting physearth-eval or physearth-knowledge off as their own distributions. So the honest destination is not the four-package D. It is C, plus possibly one extra package later:

C            one distribution: physearth
   ↓         only if a third party must register models standalone,
   ↓         or a model's dependencies stop coexisting in one env
C+           two distributions: physearth + physearth-models
   ↓         only if a second deployable actually exists
D            four distributions, workspace, CI matrix

Section 05Making C a rename away from D

Four decisions taken during C — none of which cost extra time — reduce the eventual C→D step from 6 days to about 4, and make C+ nearly free.

Decide in CDo thisWhy it matters for D
Dependency directionNever let models/ import from the rest of the package. Cut the pywatershed adapter → config back-edge now; pass the state directory in as an argument.This is the single edge between today and a standalone model distribution. One afternoon in C; a blocking refactor under D.
Private symbolsReplace diagnostics's import of _ensure_smrt_importable with a declared warmup() hook on the registry contract. Cross-package imports of underscore-private functions are exactly the thing that makes a split fail late and confusingly.
The facadeOne backend/physearth/api.py that the frontend may import, and a test asserting the frontend imports nothing else.It becomes the core package's public surface unchanged. Without it, D means designing a public API under deadline.
Content resolutionOne paths.py resolving knowledge/, models/ and prompts/, working from a checkout and an installed wheel. Under D the same function resolves across distributions. The call sites never change.
